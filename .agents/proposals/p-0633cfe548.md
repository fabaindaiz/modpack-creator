An artefact installed on a host is identified by a digest of its bytes looked up in the registry it came from, never by the name and version it declares about itself. Self-declared identifiers are chosen by each author in a namespace the registry does not own: they collide across projects, their version strings follow per-project conventions the registry does not share, and one declared version can map to several published files (one per platform). Not when the registry indexes the declared identifiers itself and guarantees their uniqueness. Cost: a digest needs the whole file, which is a full download when the host exposes no checksum; caching the digest by (path, size, modification time) bounds that cost, at the price of the stale-cache boundary of `derived-copy-goes-stale-silently`.

## Evidence

2026-10: a service that must tell which plugin packages a remote host has installed, where the host's file API returns names, sizes and timestamps but no checksums. A probe over nine real packages from one public registry compared two lookups. Lookup by the identifier and version each package declares in its own manifest resolved four of nine exactly. One declared name resolved to an unrelated project of another type that owned that name in the registry. One resolved to the build for a different platform with the same version string. Three were not found because the registry's version strings carry a different prefix or suffix than the manifest's. Two names did not exist as registry slugs. Lookup by a SHA-1 of the file bytes against the registry's hash endpoint resolved nine of nine. The open-source clients examined (two launchers, the registry's own desktop app and a command-line updater) all identify by file digest; one parses the manifest for display only. Literature: content addressing as in Git's object model (https://git-scm.com/book/en/v2/Git-Internals-Git-Objects), where an object's name is the hash of its content. That is the same principle this note states for identifiers that cross a boundary.
