A contract test that checks only the fields a request carries can pass while the request changes a value on the way: an HTTP client may encode a field it was handed as plain text, and a receiver that does not decode keeps the encoded form. A multipart form builder can percent-encode an uploaded file's name by default; a file server that stores the name as sent then saves `a+b.jar` as `a%2Bb.jar`, and every later step that looks for the original name fails. Check in the contract the exact value the receiver sees for anything that becomes an identifier on the other side (a file name, a path, a key), with an input that contains the characters an encoder touches, and run at least one end-to-end test through the real client against a server that behaves like the receiver. Not when the receiver is specified to decode the value, and a test shows that it does.

## Evidence

2026-10: a service uploaded files to a game-server node through signed multipart URLs. The contract test asserted the form field and the bytes, with a plain file name, and passed. An end-to-end test that ran the whole update procedure through the real HTTP client against a local server failed at the staging check: the uploaded name had become percent-encoded, because the client library quotes multipart field values by default, and most real artifact names carry a `+`. The node stores names as received. Disabling the quoting fixed it, and the contract test now uses a name with `+` and asserts it arrives unchanged. Literature: the client library documents an option on its form builder that quotes field values, on by default (https://docs.aiohttp.org/en/stable/client_reference.html#formdata); RFC 7578 §4.2 notes that percent-encoding of file names in multipart is not interpreted by all receivers (https://www.rfc-editor.org/rfc/rfc7578#section-4.2).
