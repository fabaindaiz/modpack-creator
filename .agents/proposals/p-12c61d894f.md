A client that decodes a body from every response turns every bodyless success into an error, and a retry around that client turns the error into a repeated action. Many write endpoints answer 204 No Content; decoding JSON from an empty body with no content type raises, the client reports a failure, and a retry decorator sends the write again. For a write with side effects (power a machine, delete a file, run a command) the effect happens twice and the caller is told it never happened. Treat an empty body as no data rather than as an error, read the status for success, and never retry a non-idempotent write on a generic exception. A contract test per call against a local server that answers exactly as the specification says (including the empty 204) catches it; a test against a double that returns JSON for everything does not. Not when every endpoint the client calls is specified to return a body.

## Evidence

2026-10: an HTTP client for a game-server panel decoded JSON on every response. Power, command and delete endpoints answer 204 with no body; each real success raised a decode error, and the methods carried a retry decorator over any exception, so a restart would have been sent twice and reported as failed. Nothing called those methods yet. Contract tests against a local server returning the specified 204 failed on all three; the fix decoded only non-empty bodies, removed the retries, and made a retried write an audit failure. Literature: HTTP semantics define 204 as a response with no content (https://www.rfc-editor.org/rfc/rfc9110#name-204-no-content); the client library raises on a JSON decode when the content type is not JSON (https://docs.aiohttp.org/en/stable/client_reference.html#aiohttp.ClientResponse.json).
