Whether an undo is still available is a function of the whole history of the thing it undoes — every later attempt, every earlier undo, and whether each succeeded, failed or never wrote — so every rule about it (*a later operation supersedes*, *an undo does not supersede what it undoes*, *only an operation that wrote supersedes*) has to be checked against every short sequence of events, not against the sequence that motivated it. Each such rule is local and reads as obviously right; its defects are in sequences nobody wrote down, and they come in both dangerous directions: an undo offered when it would destroy work (repeating a restore that already ran), and an undo refused when it is the only way out (the second-level recovery after the first failed). Before accepting a change to such a rule, write the transition table — states, events, outcomes, what is offered after each — and enumerate sequences up to a small length in a table-driven or stateful property test, so the next rule change is checked against all of them. Not when the operation has a single undo that is always available or never, with no outcomes in between. Cost: a table to maintain beside the rules, and a test that grows with the number of event kinds.

## Evidence

2026-10, in a service that updates a remote host with two recovery modes on request (put the old files back, or restore a backup, which loses work done since the backup). Three successive edits to the rule of which update may still be rolled back were each right for the case that prompted them, and each opened another sequence, found by a review rather than by a test: (1) *refuse a rollback of a superseded update*, with *superseded* read as *anything later*, made a failed first-mode rollback the latest event, so the second mode for the same update was refused and the host stayed stopped with no recovery in the application; it also let an attempt refused before writing anything orphan an earlier update that had written; (2) the fix — a rollback never supersedes the update it undoes, and only an update that reached its writing steps supersedes — made a successful rollback leave the update open, so the application offered both rollbacks again, and a repeated backup restore would have discarded the work done since the first one (found by the re-review of the fix wave); (3) the owner then fixed the rule by hand: a failed rollback closes nothing, after a successful first mode only the second is offered, with a warning and a typed confirmation, after a successful second mode nothing, and any later real update supersedes whether or not it wrote, which the owner accepted would leave some recoveries to be done by hand outside the application. A later review also found that this last consequence was applied silently: no dialog said that confirming an update discarded a pending rollback.

### Literature

Stateful property-based testing generates sequences of actions to find the one that fails, rather than testing hand-picked sequences (Hypothesis, "Stateful tests", https://hypothesis.readthedocs.io/en/latest/stateful.html; MacIver, "Rule Based Stateful Testing", https://hypothesis.works/articles/rule-based-stateful-testing/). The repository did not adopt it; the rules are tested by hand-written sequences.
