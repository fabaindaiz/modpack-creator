When work is split into tasks, each implemented by a fresh agent and reviewed against its own brief, a review of the merged change after the last task finds defects that no task review could: they live where one task's rule meets another task's flow, and a reviewer given one diff and one brief does not hold the other half. Schedule the whole-change review as a required step, not a formality after green task reviews, give it the merged diff and the decisions it implements, and re-review the fix wave it triggers, because a fix to a cross-task defect is itself a cross-task change. Not when the tasks share no state, interface or rule (independent files with no caller in common). Cost: one long review per plan and one more after its fixes; the per-task reviews stay, because they catch the local defects cheaply and early.

## Evidence

2026-10, in one repository, across three consecutive plans of a web-panel project run task by task (a fresh implementer per task, a review of each task against its brief, fix rounds, then a review of the whole branch). In the first plan about two in five task reviews found an Important defect in their own task (a refusal that accepted one header value it should not, pagination that skipped equal timestamps, a read-modify-write that lost concurrent edits, a real operation not bound to the build it was previewed with). The whole-branch review then found three more Important defects, each spanning tasks: a rollback rule from one task blocking the recovery path another task's flow relied on, an identity rule refusing users the login flow of a third task admitted, and a security rule that silently withdrew a capability an earlier decision granted. Its fix wave was re-reviewed and the re-review found one Important defect the fix itself introduced (a recovery offered again after it had succeeded). In each of the next two plans the final review again found cross-task defects the task reviews had passed: a configuration value silently disabling a scheduled job, a lazily loaded fragment firing on every page load, an implicit consequence of a rule applied without warning the operator, and a migration procedure broken for the oldest supported version.

### Literature

In a study of review at one large company, understanding the change was the key aspect of reviewing and the need reviewers' tools met least (Bacchelli and Bird, "Expectations, outcomes, and challenges of modern code review", ICSE 2013, https://www.microsoft.com/en-us/research/publication/expectations-outcomes-and-challenges-of-modern-code-review/); a per-task reviewer's understanding is bounded by its brief.
