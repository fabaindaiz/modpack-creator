The note's experiment on the one modification-time-keyed step in this repository: a scan cache that skips re-downloading a remote file whose (path, size, modification time) equals the previous scan's entry, with a periodic full scan that trusts no cached entry. Its pure planning function was run with a cached entry and a listing of the same path whose content had changed, under four timestamps: older, newer, identical, and identical except for a sub-millisecond difference; then once in full mode.

## Result

2026-10-04. Older-dated edit: noticed (re-hashed). Newer-dated edit: noticed. Identical size and time: missed — the stale hash is kept. A difference below one millisecond: missed, because the key is normalised to the store's millisecond precision so that it survives a round trip through the store. Full mode: noticed. Verdict moves the boundary: the older-dated-copy failure the note describes belongs to *newer-than* comparisons; an *equality* key over modification time and size notices an older-dated edit, and its blind spot is an edit that preserves both — a same-size replacement given exactly the old time — widened to the storage precision of the timestamp. The module's own documentation names a restore that keeps old timestamps as invisible to the cache; the run shows that case is noticed whenever the restored time differs from the one the last scan stored, so the documented blind spot is wider than the real one. The remedy in place is the bounded staleness the note's *Not when* allows: a scheduled full scan re-hashes everything. Cost: minutes.
