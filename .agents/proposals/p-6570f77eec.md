A specification read through a fetch tool that answers a question about the page with a model is a summary, not the primary source, even when the address is the primary source's. Summaries of machine-readable contracts fail exactly where a client is decided: the shape of a response (one object or a map), which parameters are required, which status carries no body. When the source is machine-readable (an OpenAPI document, a schema, a grammar), download it whole and read the fact with a parser — the path, the method, the response schema — and cite what the parser returned; use the summary only to find where to look. Not when the source is prose with no structure to parse, where the remedy is to quote the sentence rather than paraphrase it. This sharpens the method's *prefer the primary source over a summary*: an agent can believe it followed that rule while reading a summary of the primary source.

## Evidence

2026-10, in a service whose HTTP clients were being checked against the providers' published specifications before contract tests were written. The fetch tool's answer about one endpoint of an OpenAPI document said that a lookup by hash returned a map from hash to object; reading the same YAML file with a parser showed that the single lookup returns one object (the batch variant returns the map). The client and its contract test were written from the parsed document, and the session recorded the discrepancy.

### Literature

The fetch tool's own description says it converts the page and "answers prompt against it using a small fast model", i.e. its output is a model's answer about the page; the method's research phase asks to prefer the primary source over a summary (`prompt-bootstrap.md`, Phase 2). No study of summarisation error on API specifications was found.
