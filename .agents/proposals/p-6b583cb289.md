# Proposal: a-version-bump-spends-the-forward-compatibility-it-was-protecting

A new optional field that enters the digest of a stored record must leave the digest when it is empty, and be put in a fixed order when it is a set. Otherwise every record stored before the field existed reads as stale on the first deploy, and a set whose iteration order follows the process's hash seed gives a different digest on every restart.

## Evidence

2026-10-13, one carrier: two optional fields (a set of enabled options and a set of marked items) were added to the request whose digest tells a stored result from a stale one. Both were dumped as they were, empty lists included and the set unsorted, so every stored result would have read as stale after the deploy, and with two or more marked items the digest changed from one process to the next. The repository's gate was green; an isolated whole-branch review found it, and a test that reproduces the old digest by hand and one that shuffles the set now pin it. The fix leaves each field out when empty and sorts it when present, as the repository already did for an earlier optional field. Literature: the target note's own sources on forward compatibility of shipped records; no new source consulted.
