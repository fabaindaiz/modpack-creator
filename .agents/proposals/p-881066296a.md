A cache keyed on a timestamp that comes from another system stops matching after the timestamp makes a round trip through a store that changes its representation. A document store commonly gives datetimes back without their time zone and truncated to milliseconds, while the source system sends them with a zone and finer precision. The key built from the fresh listing and the key built from the stored copy then never compare equal, and the cache silently misses on every run: the work it was meant to avoid is done every time, with no error. Normalize the timestamp at the model boundary to the representation the store returns (one zone, the store's precision), so both sides of the comparison pass through the same function, and test the round trip against the real store rather than an in-memory double, which keeps the original object and hides the change. Not when the key is an opaque value the store returns byte for byte, such as a content hash or a string.

## Evidence

2026-10: a service listed files on a remote host and cached their hashes keyed by path, size and modification time, so that only changed files would be downloaded again. Every second scan downloaded everything. The modification times from the remote API were zone-aware with microseconds; the ones read back from the document store were naive and truncated to milliseconds. The bug appeared only in the test that ran against a real database; a fake would have returned the original objects. The fix normalized the field in the model's validator, with a pure test comparing a zone-aware value and its stored form. Literature: the driver documentation states that datetimes are returned naive in UTC unless the client is created zone-aware, and the BSON specification stores datetimes as milliseconds since the epoch (https://pymongo.readthedocs.io/en/stable/examples/datetimes.html, https://bsonspec.org/spec.html).
