An authorization rule that fails closed on an identity-provider claim is only as open as that claim's default. When the provider ships the claim as false by default, "require it" locks every user out, and the fail-closed design that was meant to protect the system takes the whole system down. Before a rule depends on a claim, read the provider's current documented default for it. Prefer conditions the operator controls explicitly (membership of a group the operator administers) over claims whose value the provider derives on its own. Keep the derived claim only where it is the identity itself, such as an email allowlist, which needs a verified email. Not when the provider documents the claim as always asserted for the flows in use.

## Evidence

2026-10: a small web service restricted its login, which had admitted any account of its identity provider, to allowed groups or allowlisted emails, both requiring a verified-email claim. Before deployment, primary-source research into the provider found that a release about a year earlier changed that claim's default to false. With the first rule, no user could have logged in. The rule was split: group membership no longer needs the claim, and the email allowlist still does. A test was written and seen failing for each half before the fix. Literature: OpenID Connect Core 1.0 §5.1 defines the claim as the provider's assertion that it verified the address, which leaves the default to the provider (https://openid.net/specs/openid-connect-core-1_0.html#StandardClaims). This overlaps `fail-closed-defaults`, whose boundary is a configuration default; here the default belongs to an upstream system the service does not control.
