A test marked as an expected failure, strictly, still passes when it fails for an unrelated reason, unless the mark names the exception it expects. An import error, a missing fixture or a typo raises before the assertion that describes the known defect, and the runner counts that as the expected failure: the test is green while checking nothing, and the day the defect is fixed nothing tells you the test never ran its assertion. Name the exception (usually the assertion error) in the mark, so any other failure is reported as a failure. Not when the expected failure is itself an exception of a specific type raised by the code under test, which is then the one to name.

## Evidence

2026-10: a test reproducing a known defect against a real database was marked strict expected-failure until the next session would fix it. Before the database helper it imported existed, the test failed at import, and the run reported it as the expected failure. Restricting the mark to the assertion error turned the import failure into a visible error. Literature: the test runner documents that `raises` narrows which exceptions count as the expected failure, and that any other exception is reported as a regular failure (https://docs.pytest.org/en/stable/how-to/skipping.html#raises-parameter).
