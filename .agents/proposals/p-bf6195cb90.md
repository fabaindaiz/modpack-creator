A permission deny written for secret files by their name prefix also catches the committed template that lists those files' keys, and when the repository's gate requires the template to change together with the code (every required key present), every change that adds a required setting leaves the gate red until a human edits the template. An agent that correctly refuses to work around the deny cannot close the change, and if the deny sits at a wider scope than the repository (a user-level setting), the repository's own permission file shows no conflict, so reviewing it during adoption does not find the clash. At adoption, list the files the gate's rules require a change to update, and test each against the effective permissions at every scope — by asking the agent to read it — not against the project file alone; then either narrow the deny to the secret itself or record the template edit as a human step in the rule's message. Not when the template holds real values, in which case it is a secret and should not be committed. Cost: one check at adoption and whenever a new deny or a new template-coupled rule is added.

## Evidence

2026-10, in a service whose audit requires every mandatory configuration key to appear in a committed template. A user-level deny on the environment-file prefix, meant for the secret file, also matched the template; the project's own permission file denied only the secret file. A change that added a mandatory key had its agents stop and report the deny, as the repository's rule (never work around a deny) requires; the owner kept the user-level deny, and the gate, and CI with it, stayed red for about three days on that one audit rule while the rest of the work was merged.

### Literature

The assistant's settings documentation says that permission lists set in several files (user, shared project, local project) are combined rather than overridden, "so each file can add entries without removing another file's" (https://code.claude.com/docs/en/settings, *Lists merge instead of overriding*); a project file therefore does not show the effective denies.
