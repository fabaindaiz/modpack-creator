For every check in one repository's newly built gate (bundle verify, record-id check, six structural audit rules, the type checker, the test suite), whether a planted violation was seen to turn it red before it was trusted.

## Result

2026-10, in a small web service whose gate was built in one session. All ten checks were seen red in the end. One of them had been green while blind:
- **The record-id check** passed with zero errors for a whole session while recognising none of the roadmap's definitions. The roadmap followed the method's heading template, with the id before the separator; the tool reads a heading definition only after it. Duplicate detection over roughly two thirds of the ids was therefore silently off. It was noticed only because the count of definitions was lower than the number of ids written. After the headings were moved, the check turned red at once on five real double definitions, in a table whose first column held ids that were meant as citations.
- **The six audit rules** each have a test that feeds a planted violation and a clean case.
- **The type checker and the three new tests** were seen red against the real defects before those were fixed.
- **Bundle verify** was seen red on the missing carrier file.
- **A wrong-reason red:** one test was red because it asserted on a framework's internal route list, which a framework upgrade had made lazy. It was replaced by an assertion on the public schema.

Cost: under an hour. Verdict: confirms. It adds a boundary to the note's check: compare a check's count of what it examined with the number of subjects known to exist; a plant shows only that the check can fail.
